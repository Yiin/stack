Which one do I use?

Pick by the size of the work. Small work needs one command. Large work needs a plan first. A whole project with many parallel streams needs a coordinator.

You haveUse

A large goal that needs many commits/plan-epic <goal>

A whole project with many streams of work, and you give outcomes, not tasks/orchestrate

How they fit together

The rules file sits under everything. The skills stack on each other. /cook-it does one task. /cook-epic runs /cook-it once for each task in an epic. /plan-epic makes that epic. /orchestrate sits on top and runs many agents at once. The project map shows the state of all of it.

All of the skills keep their state in beads (the bd command), not in the chat. So a new session, or an agent with no memory, can continue the work.

AGENTS.md rules file

The standing rules that every agent session reads before it does anything.

An agent forgets everything between sessions. This file is how it remembers your rules. Claude Code reads ~/.claude/CLAUDE.md at the start of every session. Codex reads ~/.codex/AGENTS.md. Put the same text in both.

The most useful rule is the report format. The agent must answer in Simplified Technical English (ASD-STE100): short sentences, simple words, verdict first. Every session report answers four things: what this is about, what it did, whether you must act, and what is next. You can then read any session in 30 seconds.

Other rules in it

  • Never estimate time. Describe scope instead.
  • Never run destructive git commands. Other agents have work in the same repo.
  • Track all work in beads, not in TODO lists.
  • Guard every variable in rm and mv: "${dir:?}".
  • Never wait with pgrep -f. It matches itself.

Change before you use it

  • The machine list, the shared beads server, the token store and the local dev tools are personal. The shared copy has placeholders.
  • Add a rule each time you correct an agent twice for the same mistake.

/cook-it skill

Does one bounded task from start to finish: plan, code, review, test, commit, push, close the issue.

You give it an issue ID or one sentence. It does not ask for approval. Typing the command is the approval. It shows the plan so you can stop it if the plan is wrong.

The important part is that it scales the checks to the task. A one-line fix gets no plan and a self-review. A change across many files gets a written plan, a critic agent, and several reviewer agents. Before it starts, it makes four decisions and says why for each one:

  1. Does the task need a written plan, or is the issue text already a plan?
  2. Does the plan need a critic? Yes when it adds a second path next to an existing one, changes a contract, or spans more than about 3 files.
  3. What review does the code need? From "the evidence is enough" up to one reviewer per part of the change.
  4. Does the change need a tester agent to drive the real app? Yes when users can see the change and the repo says how to run the app.

The reviewers always check "parity". When new code copies the job of old code, the reviewer opens the old code and lists every step it does. Missing steps are the bugs that a diff does not show.

Use it when

  • The task is concrete: a bug fix, one feature, a refactor.
  • You can describe "done" in one or two sentences.
  • You give it an epic ID. Then it does exactly one child of that epic and stops.

Do not use it when

  • You do not know yet what you want. Talk it through first.
  • The task needs an architecture decision that only you can make.
  • The tests already fail for other reasons.
  • The work needs many commits. Use /plan-epic.

/plan-epic skill

Turns a large goal into an epic: one parent issue with ordered child issues, each one a single commit of work.

An epic is a parent issue in beads. Its children are the tasks. Dependencies between children set the order. A child can start only when the children it depends on are closed.

  1. It asks you 1 to 3 questions only when the answer changes the plan.
  2. It starts 3 to 6 investigator agents in parallel. Each one reads one area of the code and proposes child tasks.
  3. It merges the proposals, removes duplicates, and sets dependencies. Each child text is complete, because a fresh agent will build it from that text alone.
  4. It writes a short orientation card into the repo (docs/agent-orientation.md): paths, check commands, traps. It commits the card.
  5. It writes a "Handoff Protocol" into the epic itself. Any agent that opens the epic later knows the goal, the rules, and what to do next.
  6. It gives you one command: /cook-epic <id>. If you said "plan and run it", it starts the run itself.
Set order with dependencies, not with priorities. The runner picks any ready child. A child that must come first must block the others. A false dependency makes parallel work run one at a time.

Use it when

  • The work is bigger than one /cook-it task.
  • You want to run it later without you.
  • You want the plan and the progress in one place that survives new sessions.

Do not use it when

  • It is one task. Use /cook-it.
  • You are still asking "what should we do here?"

/cook-epic skill

Runs every child of an epic while you are away, one fresh agent per child.

The skill starts simmer, a small runner program. simmer runs in the background and does not need the chat. For each child that is ready, it:

  1. Makes a new git worktree, so the worker cannot touch your checkout.
  2. Starts a fresh agent with no memory. The agent runs /cook-it on that one child.
  3. Checks three facts: the agent made commits, the agent closed the issue, and the full test gate passes.
  4. Merges the work into the base branch. It pushes only if you set push: true.

A child that fails twice gets status "blocked" with the error in a note. The run continues with the next child. All state is in beads. If the run crashes, run the same command again and it continues.

Check progress from any terminal with simmer status <epic>.

Use it when

  • An epic exists and bd ready --parent <epic> shows tasks.
  • The repo has a test command that a script can run. The default gate is bun run typecheck && bun run test. Set yours in simmer.json.

Do not use it when

  • There is no epic yet. Run /plan-epic first.
  • The tasks need your taste or your decisions while they run.
You need simmer. simmer is a private tool and is not in the download. Ask for access. Without it, you can still run an epic by hand: type /cook-it <epic> again and again. Each run does one child.

/orchestrate skill

Makes the agent the lead of the project. It plans, delegates, checks and reports. It writes no code itself.

You give outcomes, such as "make the maps look incredible". The coordinator cuts them into lanes. A lane is one piece of work with one agent, one issue, one worktree, one log and one review page. Each lane gets a fresh agent and a full written brief, from a template. Lanes run in parallel, but never on the same files.

  1. Brief. Each brief has your exact words, the facts already known, the decisions already made, the scope, the proof that counts as done, and the other lanes to avoid.
  2. Check. Agents over-claim. The coordinator checks that work is really merged and that it fixes what you saw.
  3. Decide. It makes technical decisions itself and records them. It asks you only about money, taste, things that cannot be undone, and other people. Each question has a default, so work does not stop.
  4. Watch. A watchdog script reports stuck lanes, a deploy, or low memory.
  5. Route. Work with a clear spec and a test goes to Codex. Work that needs taste, screenshots or writing for you goes to Claude. This saves Claude usage.
  6. Release and report. It ships often and reports in 30-second summaries with a link to each review page.

Use it when

  • The project has many streams of work at once: art, physics, tools, releases.
  • You want to give direction, not tasks, and check in from time to time.
  • The work runs over hours or days.

Do not use it when

  • The work is one epic with clear order. Use /cook-epic.
  • It is one task. Use /cook-it.
The skill expects a folder per project, projects/<name>/, beside SKILL.md. It holds that project's README, lane rules, watchdog and Codex runner. The coordinator creates the README as it learns the project. The download has the two templates and an example Codex runner, not the private project folders.

project-map subagent

Draws one HTML page that answers "where are we?" for the project.

A subagent is a helper agent with its own instructions and tools. The main agent starts it. This one reads the code, the git history and the issues. Then it writes .project-map/index.html in the repo.

  • Parts: 3 to 8 main parts, each done, in progress, not started, or stuck. A stuck part names what it waits for.
  • Proof: a part is "done" only with proof. The agent runs the tests and takes screenshots. No proof means "in progress".
  • Next step: the smallest action that moves the next milestone forward.
  • Needs your call: open questions, each with a default and what the agent does while it waits.

It can write only inside .project-map/. A hook script blocks every other write.

Use it when

  • Before a long run without you. Start it in the background.
  • After each milestone.
  • When you ask "where are we?"

First run

  • Run it in the foreground once. It asks for dark or light and one accent color, then saves the answer.
  • It needs jq and git for the hook.

Install

These commands copy the skills, the subagent and the hook into Claude Code. They do not touch your current CLAUDE.md.

curl -fsSL https://stack.yiin.lt/stack.tar.gz | tar -xz
mkdir -p ~/.claude/skills ~/.claude/agents ~/.claude/hooks
cp -rf stack/skills/* ~/.claude/skills/
cp -f stack/agents/* ~/.claude/agents/
cp -f stack/hooks/project-map-guard.sh ~/.claude/hooks/
chmod +x ~/.claude/hooks/project-map-guard.sh

Then open stack/AGENTS.md. Change the personal sections to match your setup. Save it as ~/.claude/CLAUDE.md, or add its rules to the file you have.

For Codex, copy the skills to ~/.agents/skills/ and the rules file to ~/.codex/AGENTS.md. The subagent and the hook work only in Claude Code.

What else you need

  • bd (beads). All four skills use it. Run bd init in each repo.
  • simmer for /cook-epic. Private. Ask for access.
  • Optional: the Codex CLI, for Codex lanes in /orchestrate.
  • Optional, for project-map: the ui-ux-pro-max skill and the unslop skill from pstack.

Words used on this page

Skill
A folder with a SKILL.md file. You start it with /name. The agent then follows its instructions.
Subagent
A helper agent that the main agent starts. It has its own instructions, tools and empty memory.
beads, bd
An issue tracker that agents use from the command line. Issues live in the repo or on a shared server.
Epic
A parent issue. Its children are the tasks.
Ready
A child whose dependencies are all closed. Only ready children can start.
Worktree
A second checkout of the same git repo in another folder. Agents work there so they do not touch each other's files.
Gate
The full check command: typecheck, lint and tests. Work merges only when the gate passes.
Lane
In /orchestrate, one piece of work with one agent, one issue and one worktree.
Fresh context
A new agent with empty memory. It knows only what its brief or issue says. This is on purpose: a short, complete brief beats a long, full memory.
